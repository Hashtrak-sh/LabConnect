# QR codes and public verification

**Status:** DRAFT for gate G1/G2.

## 1. Payload formats
QR payloads carry **IDs and a signature only**. No names, batches or results (FS §8.1).

| QR | Payload | Example |
|---|---|---|
| Booking | `LC1.B.<bookingNo>.<keyId>.<mac>` | `LC1.B.LC-2611-0004821.k3.9F2K…` |
| Package | `LC1.P.<bookingNo>.<seq>-<total>.<labelVer>.<keyId>.<mac>` | `LC1.P.LC-2611-0004821.1-2.1.k3.Q7MZ…` |
| Report | URL `https://<public-host>/v/<verificationCode>` | `https://…/v/7GQ2X9KD4M1TRV8B` |

- `mac` = first 128 bits of `HMAC-SHA256(key, canonical_string_without_mac)`, Crockford base32. Computed by **AWS KMS `GenerateMac`** with an HMAC_256 key per purpose. The key material never leaves KMS.
- Verification on scan uses **`VerifyMac`** server-side (never trusted on the client). Results are cached per payload for 5 minutes in Redis to limit KMS calls.
- `keyId` maps to `qr_signing_key`. During rotation, the old key goes to `VERIFY_ONLY` for the longest package validity (90 days), then `RETIRED`.
- Rotation: quarterly (FS §13.2) via a runbook procedure (`07-operations/RUNBOOK.md` §6).
- The report QR has no MAC because the verification code is a random, unguessable server-side lookup key. The authenticity check is the server lookup plus the hash comparison.

## 2. Labels
- Each label shows the QR, booking number, package `n/N`, the **6-character short code** (Crockford base32, unique among active packages) and the lab site name. Nothing about the customer or item.
- Formats: A4 sticker sheet (e.g. 2×7) and 50×25 mm thermal. PDF generated by the worker and cached per label version.
- Printable by the customer (any time after HANDOVER_SET) and by the lab Maker at the counter (CD-12). Every print or reprint is logged (`label_print`). A **reprint** increments `label_version` and voids the earlier version, so scanning an old label returns `PACKAGE_VOIDED`. Lab reprints need Checker approval (EC-26).

## 3. Scan validation (`POST /v1/custody/scan`)
In order: parse → known key and status allows verify → `VerifyMac` → booking exists → booking site = the actor's site (otherwise `QR_WRONG_SITE` with the intended site's public name and address) → booking state ∈ {HANDOVER_SET, ON_HOLD (replacement)} → package not voided and not already received. Every outcome writes a `custody_event` (`SCAN_ACCEPTED` / `SCAN_REJECTED` with reason).
Manual fallback: short-code lookup (`MANUAL_LOOKUP` event, photo required).

## 4. Browser scanner (lab web app)
- The camera is accessed with `getUserMedia`. Decoding uses a maintained JS library (pin the version, evaluate `zxing`-based or `BarcodeDetector` with a fallback).
- **Offline queue**: when the network fails, scans are stored in IndexedDB with `deviceId`, `clientRecordedAt` and a monotonic `clientSeq`, then synced via `/custody/scan-batch`. The server orders by `clientSeq` and flags a skew of more than 15 min (EC-50). Offline scans are provisional until the server accepts them. The UI says so clearly.
- Works on Android 9+ Chrome and on low-end devices (NFR-07).

## 5. Public verification page (`/v/<code>`)
SSR page, no login, rate-limited (30/min/IP), `noindex`.

| Shown | Not shown |
|---|---|
| Result: **Genuine – current**, **Genuine – superseded by vN** (with the date), **Not found**, **Revoked** | The PDF or any download |
| Report number, ULR, issue date, version | Customer identity, item, batch, results |
| Lab site name, city, NABL certificate number and accreditation status as of the issue date | Contact details |
| Approving Checker's name and designation (FR-RPT-08). **Data-minimisation review pending (OQ-15).** | |
| SHA-256 of the stamped file | |
| **"Compare a copy"**: the user selects a PDF, the browser computes SHA-256 **locally** (Web Crypto) and compares. **The file isn't uploaded.** | |

Every lookup writes `verification_event` (IP hashed with a rotating salt).
