# Authentication and authorisation

**Status:** Approved at gate G2 (2026-11-25). Decision: ADR-006 (in-house passwordless auth on NestJS, with Amazon Cognito recorded as an alternative).

## 1. Sign-in (MVP)
1. `POST /auth/otp/request {email}` → 6-digit OTP, 10-minute expiry, emailed via SES. The response is always 202.
2. `POST /auth/otp/verify {email, code}` → if the user doesn't exist, it's created (`ACTIVE`, email verified) for customer self-signup. Invited users accept through the invitation token.
3. If any active membership has an MFA-required role: the user must enrol (`MFA_ENROLMENT_REQUIRED`) or verify TOTP before a full session is issued.
4. Session: **access JWT** (10 min, `EdDSA`, claims: `sub`, `sid`, `amr`, `mfa_at`) and a **refresh token** (opaque, rotating, 12 h idle / 7 days absolute, httpOnly + Secure + SameSite=Lax cookie scoped to the API domain). Reuse of a rotated refresh token revokes the whole token family.

**Phone OTP** (FR-IAM-02) is added when an SMS provider with DLT registration is contracted (OQ-11). The schema already supports it.

## 2. MFA
- TOTP (RFC 6238, 30 s, ±1 step), with the secret encrypted with a KMS data key and 10 single-use recovery codes.
- **Required** for: `LAB_CHECKER`, `CUSTOMER_FINANCE`, all `PLATFORM_*`.
- **Step-up** (fresh MFA ≤ 5 min, stored as `user_session.mfa_verified_at`) for: report publish (T-21), bank account add or change, payout release, refund approval above the threshold, break-glass access, platform role changes.
- MFA reset: by `PLATFORM_ADMIN` only, after identity verification. Audited.

## 3. Authorisation model
- **Permission codes** (e.g. `booking.accept`, `receipt.approve`, `report.publish`, `masterdata.changeset.approve`) are mapped to roles in `packages/shared/src/permissions.ts`, generated from the matrix in `ROLES_AND_PERMISSIONS.md`.
- Nest guards, in order: `AuthGuard` (valid access token, session not revoked) → `MembershipGuard` (resolve the active membership, load roles and site IDs into `CurrentActor`) → `PermissionGuard(@RequirePermission)` → `MfaGuard(@RequireStepUp)`.
- **Resource checks** in the domain service: the tenant scope matches; the lab site is in the actor's `siteIds`; Maker ≠ Checker on the target record; the state allows the action.
- Unknown or out-of-scope resources → 404. In-scope but not permitted → 403.

## 4. Session security
- Revoke on: logout, membership deactivation (all sessions for that membership's user, when the session's active membership is the one revoked), role change, MFA reset, detected refresh-token reuse.
- Device list via `user_session`. Anomaly signals (new country or ASN, many failed OTPs) are logged and alerted.
- CSRF: the API accepts the cookie only on `/auth/refresh` (SameSite=Lax + `Origin` check). Other calls use the bearer token held in memory by the web app.

## 5. Lab claim verification (FR-DAT-07)
The OTP is sent to `lab_site_private.contact_email` (SCHEMA_SPECIFICATION §5.17; this paragraph used to say `lab_site.contact_email`, a column that does not exist) from **NABL-imported data only** (never a user-supplied address). Fallback: a manual letterhead upload, reviewed by `PLATFORM_OPS`. On approval, the claimant becomes the first `LAB_CHECKER` (MFA enrolment forced) and the org becomes `CLAIMED`.

**As built (I1-LAB-01 to I1-LAB-04 and I1-LAB-06: `startLabClaim`, `verifyLabClaimOtp`, `createLabClaimLetterheadUploadUrl`, `submitLabClaimLetterhead`, and their abuse limits).** Core: `packages/core/src/labs/claims.ts`; API: `apps/api/src/modules/labs/lab-claims.*`. The Ops side (list, approve, reject) is the next block; a way for Ops to open the letterhead is not built (OQ-225).
- **Who may call.** Any signed-in user, also one with no membership (`@Authorised({ noPermissionRequired: true })`; a new lab user has none until Ops approves). Platform staff are `403 FORBIDDEN` (RR-5) on `startLabClaim`, by the actor and by `app_user.is_platform_staff`, before any lookup. `verifyLabClaimOtp` has no such check: the contract documents no 403 for it and staff cannot hold a claim, so it is `404` for them. No value of the request names an organisation: it is the organisation of the site found by certificate number.
- **Which lab.** A certificate number is matched exactly (after trimming) against the accreditations of **listed** sites: the public directory rule (FR-DAT-06: `LISTED` or `BOOKABLE`, `ACTIVE`, organisation an `ACTIVE` lab, accreditation `VALID` and in date today in IST, a scope line in force), read as an anonymous visitor, so the answer can name nothing a visitor cannot already see. An unknown, expired, suspended, hidden or ambiguous (two listed sites hold the number) certificate is the same `422 VALIDATION_FAILED` (OQ-205). A claimed organisation is `409 INVALID_STATE_TRANSITION` with `meta.currentState: CLAIMED`; another user's open claim is `409` with `CLAIM_PENDING` (never whose, never how far); the caller's own claim in review is `409` with `PENDING_REVIEW`.
- **Where the code goes.** Only to `lab_site_private.contact_email` of the site the claim was opened with. The request body has no address field and unknown fields are `422`. The response shows it masked (`maskEmail`): the first character of the local part, `***`, `@`, `***`, `.` and the last label of the domain (`q***@***.in`); no length, no domain name. The address and the code appear in no response, audit row, outbox payload, error or log line (tests read all of them). A site with no usable address (missing, or not shaped like an address) gives a `MANUAL` claim that stays `PENDING_OTP` with `otpSentTo: null` and sends nothing, for the letterhead route (OQ-212).
- **The code.** The identity machinery with purpose `LAB_CLAIM` (`requestOtp` and `consumeOtp` in `identity/otp.ts`, shared with sign-in): HMAC at rest, bound to the challenge, `context_id` = the claim id, 10 minutes, 5 wrong guesses lock it (`429 OTP_LOCKED`), 5 per 15 minutes per address (`429 RATE_LIMITED`, counted per purpose) and 20 per hour per IP (shared with sign-in). A new code closes only the open codes of the same claim. A rate-limited request rolls back, so it leaves no claim. The code is mailed after the commit through `OtpMailer.sendLabClaimOtp`, never through the outbox, `notification` or a template. If the send fails the claim stays `PENDING_OTP` and the caller gets `500`; calling `startLabClaim` again returns that claim with a new code (`200`). The failed attempt counts towards the limits (OQ-211).
- **State.** `PENDING_OTP` to `PENDING_REVIEW` on a correct code, in one transaction with the audit row (`lab_claim.start`, `lab_claim.code_resend`, `lab_claim.verify_otp`) and the outbox events (`lab_claim.started`, `lab_claim.pending_review`; ids and states only). There is **no notification** for either (the matrix has no row, OQ-207); Ops finds the claim in the admin queue (I2-ADM-01, below). While a claim is open `organisation.claim_status` stays `UNCLAIMED`: the open `lab_claim_request` row, held to one per organisation by `uq_lab_claim_request_pending`, is what marks the organisation taken; nothing sets `CLAIM_PENDING` yet, and no membership exists until approval. Two users racing for one organisation: the insert is `ON CONFLICT DO NOTHING` on that index, exactly one wins and the other gets `409`. A `PENDING_OTP` claim never expires by itself (no document gives a rule; the `EXPIRED` status is unused, OQ-206).
- **Order of the checks of `verifyLabClaimOtp`.** `404` (not the caller's claim, indistinguishable from an unknown id; the lookup is by `requested_by_user_id`), `409` (not `PENDING_OTP`, with `meta.currentState`; so repeating a verify is `409` whatever `If-Match` says), `412` (`If-Match` is not the `lock_version`, before a guess is counted), then the code (a wrong, expired or locked code is committed as an attempt and then raised: `422 OTP_INVALID`, `422 OTP_EXPIRED`, `429 OTP_LOCKED`), then one `UPDATE ... WHERE status = 'PENDING_OTP' AND lock_version = <If-Match>` that sets `lock_version = lock_version + 1`; no row (a concurrent change) is `412` and rolls the spent code back.
- **ETag and If-Match.** Both operations return `ETag: "<lock_version>"`; a resend does not change it. `If-Match` is required on verify; a missing header, or anything but one strong `"<digits>"`, is `400` (the catalogue has no 428, OQ-209). Helper: `apps/api/src/common/etag.ts` (`formatEtag`, `parseIfMatch`, `assertIfMatch`), shared with the other modules.
- **Idempotency-Key** is accepted and ignored, as on the identity routes (OQ-87). A repeated start sends a new code for the same open claim; a repeated verify of a verified claim is `409`. Both handlers carry a `TODO(I1-SHR-01)` where the shared decorator goes.
- **The letterhead route (I1-LAB-03, I1-LAB-04).** `POST /lab/claims/{id}/manual/upload-url` and `POST /lab/claims/{id}/manual`, same `@Authorised({ noPermissionRequired: true })`, no `Idempotency-Key` handling (`TODO(I1-SHR-01)` on each handler). Allowed for **every** claim of the caller that is `PENDING_OTP`, with or without a code: the contract restricts only the state, and submitting flips the method to `MANUAL` (OQ-214). Another user's claim, an unknown id and platform staff are the same `404`; any other state is `409` with `meta.currentState`. Upload: a `KYC_DOCUMENT` through `FileService.requestUpload` (PDF, JPEG or PNG, 1 byte to 10 MB; anything else `422 VALIDATION_FAILED` naming `contentType` or `sizeBytes`), the contract's `FileUploadUrl` and nothing more, `Cache-Control: no-store`; the presigned URL is made after the commit and never logged or stored. **The file has no owning organisation** (`owner_org_id`, `customer_org_id`, `lab_org_id` all NULL), so by the policy `file_visibility` only the platform and the system context can read or insert it: no member of any organisation, the claimed lab's later members included, sees it (OQ-213). It is tied to the claim by a `file_link` row (`lab_claim_request`, role `CLAIM_LETTERHEAD`) written in the upload transaction. Submit, order of the checks: `404` (claim), `409` (not `PENDING_OTP`, whatever `If-Match` says), `412` (`If-Match` is not the `lock_version`), `404` (no file with this id that this caller requested for this claim: uploader, purpose `KYC_DOCUMENT`, no owner, the link), `422 FILE_NOT_CLEAN` (scan pending, failed, infected or rejected; the claim does not move), then one `UPDATE ... WHERE status = 'PENDING_OTP' AND lock_version = <If-Match>` setting `PENDING_REVIEW`, `MANUAL`, `authorisation_file_id` and `lock_version + 1` (no row: `412`); `200` with the claim (`otpSentTo: null`) and the new `ETag`. The code route uses the same conditional update, so a code and a letterhead racing for one claim give one winner and a `409` or `412` to the other; once the claim has left `PENDING_OTP`, `verifyLabClaimOtp` is `409` before it touches the code (no attempt is spent). Audit rows `lab_claim.letterhead_upload_requested` and `lab_claim.submit_letterhead` (ids, states and the file id; no file name, key or URL) and the outbox event `lab_claim.pending_review` (now with `method` and `fileId`) in the same transaction as the change. Upload URLs are limited per claim (the abuse limits below, OQ-217). `organisation.claim_status` and memberships are untouched.
- **Abuse limits (I1-LAB-06; decided by the product owner on 2026-11-26 for the MVP, can be reopened).** The numbers are the constants `CLAIM_LIMITS` in `packages/core/src/labs/claim-limits.ts` (they may later move to `config_parameter`; not built). No contract change: every answer below is one the contract documents for the operation.
  - **1. An unverified claim expires after 24 hours.** A claim still `PENDING_OTP` whose `created_at` is 24 hours or more behind the injected clock is expired: at exactly 24 hours it is expired, one millisecond earlier it is not. There is no timer: expiry is lazy, applied by whichever claim operation meets the claim, in its own transaction and before its own work, with `UPDATE ... WHERE status = 'PENDING_OTP' AND lock_version = <read> AND created_at <= <cutoff>` (it bumps `lock_version`), the audit row `lab_claim.expire` and the outbox event `lab_claim.expired` (ids and states only; the actor is the person whose request met the claim). `startLabClaim` expires the caller's own stale claims (any organisation) and the stale claim on the target organisation, whoever opened it, and goes on as if none were open: a new claim, `201`, also over the caller's own stale claim (a new claim, not a new code on the old one). `verifyLabClaimOtp`, the upload URL and the letterhead submit on the caller's own stale claim set it `EXPIRED` and answer `409 INVALID_STATE_TRANSITION` with `meta.currentState: "EXPIRED"`; the function *returns* the refusal as an outcome (`CLAIM_EXPIRED`, the pattern of a spent code attempt) so that the expiry commits, and the API raises it after the commit; no code is consumed. The check is part of check 2 (state): after `404`, before `412` and before any code is consumed. `PENDING_REVIEW` never expires here: it waits for Ops. Two operations racing over one stale claim: the conditional update lets exactly one expire it, the other re-reads and answers from the new state, and the partial unique index still allows one open claim per organisation.
  - **2. One person holds at most three open claims**, open meaning `PENDING_REVIEW`, or `PENDING_OTP` and younger than 24 hours, across all organisations. Only a `startLabClaim` that would insert a claim is refused: `429 RATE_LIMITED` with no `Retry-After` (the header is optional in the contract and there is no meaningful wait) and a text that names no lab, address or number. A new code for the caller's own open claim creates nothing and is still allowed. Order in `startLabClaim`: platform staff, listed site, `CLAIMED`, then the advisory lock on the user (`pg_advisory_xact_lock`) and the expiry of the caller's own stale claims, then the open claim on the organisation (the `409`s, or a new code for the caller's own), then the cap, then the insert. Every refusal that existed before is therefore answered as before, and the `429` says nothing about the lab or about anyone else's claim. The advisory lock makes one person's starts run one after the other, so two simultaneous starts cannot both take the last place.
  - **3. At most five letterhead upload URLs per claim.** Counted as the `file_link` rows (role `CLAIM_LETTERHEAD`, removed links included) of the claim, whatever became of the files (clean, infected, never uploaded). The sixth is `429 RATE_LIMITED`, with the same rules for `Retry-After` and the text. Order for the upload URL: `404`, `409` (with the expiry above), then the claim row is locked (`FOR UPDATE`) and its state read again, then the count, then type and size (`422`), so six simultaneous requests give exactly five and the claim cannot move on between the check and the insert. Submitting one of the five files still works at the limit. The allowance is per claim; a per-user cap on upload requests is not built (OQ-217).
  - **Rolled back with a refused start.** An expiry written by a `startLabClaim` that is then refused (a `409`, the cap, a rate-limited code) is rolled back with it. Nothing depends on that: every check reads a claim by its age, not by the stored status alone (OQ-220, OQ-223).
- **Database context.** One `system` transaction per operation (`LabClaimsService`, four `runAsSystem` calls, listed in `system-context.sources.spec.ts`), after an anonymous public read to find the site (start only). Reason: the claimant belongs to no organisation, so the `app_is_org(organisation_id)` policies of `lab_claim_request` and `lab_site_private` hide those rows from them, and `otp_challenge` is `platform_only`. A `tenant` context carrying the claimed organisation would open every table of that organisation and would take its id from a lookup rather than a membership. Every query in `claims.ts` is scoped by hand instead: a claim is read only with `requested_by_user_id` = the caller, and the letterhead file only by id + uploader (the caller) + purpose + no owner + its link to that claim. The letterhead operations use `system` for one more reason: a file with no owner can be inserted only by the platform or the system (`WITH CHECK (app_is_privileged() OR owner_org_id = app_org_id())`).

**As built (I2-ADM-01 to I2-ADM-03: the Ops side, `listAdminLabClaims`, `approveAdminLabClaim`, `rejectAdminLabClaim`).** Core: `packages/core/src/labs/claim-review.ts`; identity function `grantLabMembership` in `identity/memberships.ts` (shared change); API: `apps/api/src/modules/labs/admin-lab-claims.*`, paths `/v1/admin/claims`, `/v1/admin/claims/{id}/approve`, `/v1/admin/claims/{id}/reject`.
- **Who may call.** Only `PLATFORM_OPS` (the contract's `x-roles`). The guard declares `kyc.verify` ("Verify KYC and bank, approve claims"), the only permission that names claims; the matrix also gives it to `PLATFORM_FINANCE` for bank verification (note 10, condition `BANK_VERIFICATION_ONLY`), so each handler refuses every role but `PLATFORM_OPS` with `403 FORBIDDEN` first thing, before it reads a header, body or query, and the core functions check again. The three operations are in `known-admin-differences.ts` (OQ-112) and the matrix test expects the Finance refusal (`test/permissions/handler-refusals.ts`). Lab and customer roles and a user with no membership do not hold the permission: `403` from the guard, the same answer for a claim that exists and one that does not. No session is `401`.
- **Database context.** One transaction per operation in the `platform` context (`TenantScope.run` for a platform actor), not `system`: the policies allow it for every table touched (`lab_claim_request` and `lab_site_private` by `app_is_org`, `file_object` and `file_link` by `app_is_privileged`, `membership`, `membership_role` and `membership_site` by `WITH CHECK (app_is_privileged() OR ...)`, `app_user` by `app_is_privileged`; `organisation` has no policy). No new caller of `withDbContext` or `runAsSystem`. Ops acts on a claim id; the organisation, site and claimant come from the claim row.
- **What Ops see.** Exactly `AdminLabClaim`: ids (claim, organisation, site, claimant, letterhead file, reviewer), `method`, `status`, `reviewedAt`, `decisionNotes`, `createdAt`, `lockVersion` (also the `ETag` of approve and reject). No name, no address, no download link: the letterhead is opened only through the separate `createAdminLabClaimLetterheadDownloadUrl` (I2-ADM-04, OQ-225).
- **The list.** Oldest first (`created_at`, then `id`), keyset cursor (the id of the last claim, opaque), `limit` 1 to 100 (default 25), optional `status`; with no `status`, every status (the contract gives no default). The 24-hour rule (OQ-220) is applied with `isStale` and `staleCutoff` of `claims.ts`: a `PENDING_OTP` claim 24 hours old or older is shown as `EXPIRED`, `status=EXPIRED` finds it (with the stored `EXPIRED` ones), `status=PENDING_OTP` does not. The list writes nothing: the stored status stays `PENDING_OTP` until the lab side meets the claim. `422` for a bad status, limit or cursor.
- **Approve.** In one transaction, in this order, each refusal writing nothing: `403`; `404` (unknown or malformed id); the claim row locked `FOR UPDATE`; `409 INVALID_STATE_TRANSITION` with `meta.currentState` unless `PENDING_REVIEW` (a stale `PENDING_OTP` claim answers `EXPIRED`, as the list shows it, and is not expired by this call); `412` for a wrong `If-Match`; the organisation locked and set `CLAIMED` by a conditional update (`UNCLAIMED` or `CLAIM_PENDING`, an active lab; else `409`, `currentState` `CLAIMED` or the organisation's status); a `MANUAL` claim needs its letterhead, the file of this claim and `CLEAN` (`422 FILE_NOT_CLEAN`, or `422 VALIDATION_FAILED` with `meta.reason: LETTERHEAD_MISSING`); the claimant becomes `LAB_CHECKER` through `grantLabMembership`, assigned to the site of the claim (RR-3), refused with `422 VALIDATION_FAILED` and `meta.reason` `CLAIMANT_NOT_ACTIVE`, `CLAIMANT_IS_PLATFORM_STAFF` (RR-5; this also stops an Ops user from approving a claim they started), `CLAIMANT_HOLDS_LAB_ROLE` (RR-2, OQ-208) or `CLAIMANT_ALREADY_MEMBER`; then the claim row by a conditional update on `status` and `lock_version`. Audit rows `lab_claim.approve`, `organisation.claim` and `membership.create`, and the outbox event `lab_claim.approved` (the catalogue has no event for an organisation becoming claimed, so nothing consumes it but analytics; ids and states only: no notes, no name, no address). A customer-side membership does not stop the approval (RR-4); the claimant's grants are serialised by an advisory lock, so two claims of one person approved together give one lab role.
- **MFA enrolment forced.** Nothing to set: `LAB_CHECKER` is an MFA-required role (section 2), so the claimant's next sign-in is a partial session until MFA is enrolled and verified (section 1 step 3, `requiresMfa`), and an actor built from the new membership without a completed MFA is `401 STEP_UP_REQUIRED` (`buildCurrentActor`). Tested in core and over HTTP.
- **After approval.** The organisation is `CLAIMED`; its sites are as they were (`LISTED`, not bookable); KYC, bank, prices and slots are later tasks. The Checker is assigned to the site of the claim only (other sites need user management, OQ-226). The claimant is not told (OQ-207): there is no notification row and no lab-side read of a claim (OQ-209), so the decision and its notes reach the claimant only when that read exists.
- **Reject.** The same first four checks, then `decisionNotes` required and not blank (`422 VALIDATION_FAILED`, `meta.reason: DECISION_NOTES_REQUIRED`), then the conditional update; the organisation is not touched, the open claim is gone and the partial unique index no longer blocks, so the same person or another can start a new claim. Audit `lab_claim.reject`, event `lab_claim.rejected`. The lab-side `LabClaim` shows `decisionNotes` and `reviewedAt` and no reviewer.
- **Idempotency-Key** is required by the contract and not honoured yet, as on the lab side (`TODO(I1-SHR-01)` on both handlers). Both are safe to repeat by their own rule: a second decision on a decided claim is `409`.

**As built (I2-ADM-04: Ops read the letterhead, `createAdminLabClaimLetterheadDownloadUrl`, `POST /v1/admin/claims/{id}/letterhead/download-url`, OQ-225).** `PLATFORM_OPS` only, like the other three (same `kyc.verify` guard, same handler refusal of every other role before the id is read, same entries in `known-admin-differences.ts` and `handler-refusals.ts`). Core: `createLetterheadDownloadTicket` in `claim-review.ts`, one transaction in the `platform` context through `TenantScope` (not `system`). The caller sends a claim id and nothing else. The file is the claim's own letterhead: `authorisation_file_id` AND ownerless, `KYC_DOCUMENT`, with a live `file_link` of role `CLAIM_LETTERHEAD` to this claim (`findClaimLetterhead`, the predicate the approval uses, now exported and shared). Any claim status, so a decided claim can still be looked at. No letterhead (a code claim, or a file not tied to the claim) is `404 NOT_FOUND`; a file that is not `CLEAN` is `422 FILE_NOT_CLEAN` (`requireClean`) and no URL is made. The URL (15 minutes, `Content-Disposition: attachment`) is made by `FileService.presignDownload` after the commit and goes into the response only (`Cache-Control: no-store`): never logged, stored, audited or put in an event. Audit: `lab_claim.letterhead_download_url_created` (claim id, file id, the claim's status; the reviewer is the audit actor) plus the file service's own `file.download_url` entry for a `KYC_DOCUMENT`, both in the transaction of the checks; no outbox event. `Idempotency-Key` is declared by the contract and not yet honoured (`TODO(I1-SHR-01)`, OQ-87): a repeat gives a new URL and a new audit entry. No `If-Match`: nothing about the claim changes. No rate limit (no document gives one; every call is audited, OQ-233).

## 7. As built (P3-03)

Code: the logic is in `packages/core/src/identity/` (framework-free; functions take a `Prisma.TransactionClient` and a `Clock`, the caller owns the transaction). The HTTP layer is `apps/api/src/modules/identity/` (controllers, `AuthGuard`, `@CurrentSession()`, `@AllowPartialSession()`, the e-mail `OtpMailer` adapter). Where this document and the OpenAPI contract disagree, the contract wins; the differences are listed at the end of this section.

**Sign-in.**
- `requestOtp` stores `HMAC-SHA256(AUTH_HASH_SECRET, code | challenge id)` and `HMAC` of the normalised email (`destination_hash`); the code is 6 digits from `crypto.randomInt`. A new request closes the open challenges of that address, so only the newest code works. The code is sent by the `OtpMailer` port after the transaction commits; it is never written to the outbox, the audit log or a log (OQ-65). No user is read, so the answer does not depend on whether the address has an account. Limits: 5 per 15 minutes per address, 20 per hour per IP, counted in `otp_challenge` (OQ-88); a request over a limit stores nothing and gets `429 RATE_LIMITED` with `Retry-After`.
- `verifyOtp` checks the newest open challenge: 10 minutes (`OTP_EXPIRED`), 5 wrong guesses (`OTP_LOCKED`, also the CHECK of C-79; the right code is refused once locked), single use (one conditional `UPDATE`, so of two simultaneous correct submissions one wins). Then it finds or creates the user (`ACTIVE`, email verified, local part of the address as the placeholder name, OQ-93) and starts a session. A `DISABLED` user and an unknown address get `OTP_INVALID`, like a wrong code (OQ-35). An `INVITED` user may sign in and stays `INVITED` (OQ-86).
- If any active membership has a role that requires MFA (`roleRequiresMfa`: Lab Checker, Customer Finance, all platform roles), the answer is the contract's `mfaRequired` challenge: a **partial session** (access token with `pre_mfa: true`, 10 minutes, no refresh token, no cookie, `mfaEnrolled` says whether to enrol first). Otherwise a full session and the refresh cookie.

**Sessions and tokens.**
- Access token: JWT, `EdDSA` (Ed25519), header `typ: at+jwt`, `kid`; claims `sub`, `sid`, `amr` (`["otp"]`, then `["otp","totp"]`), `mfa_at` (when MFA last succeeded, absent if never), `iss`, `aud`, `iat`, `exp` (+10 minutes), `jti`; a partial session adds `pre_mfa: true`. Keys come from `AUTH_JWT_PRIVATE_KEY` (see `.env.example`); the public key is derived. `AUTH_JWT_PREVIOUS_PUBLIC_KEY` keeps old tokens valid while a key rotation settles.
- `sid` is `user_session.token_family_id`. A session is one family of rows: each refresh retires the live row (`revoked_reason = ROTATED`) and inserts a new live row with the new token's hash (OQ-92). The refresh token is 256 random bits; only its SHA-256 is stored. Idle expiry 12 hours (renewed on each refresh), absolute expiry 7 days from sign-in (`created_at` of the first row is carried forward).
- **Reuse.** Presenting the hash of a `ROTATED` row revokes every live row of the family (`REFRESH_REUSE`) and writes `auth.refresh_reuse_detected`. Two simultaneous refreshes with one token: one wins, the other counts as reuse and revokes the family, so both callers are signed out (OQ-91).
- `AuthGuard` verifies the token, then asks the database on **every request** whether the session is live (not revoked, not expired, user not `DISABLED`), so a logout or revocation works at once although the token has not expired. Every failure is the same `401 UNAUTHENTICATED`. A partial token is accepted only by handlers marked `@AllowPartialSession()`: `/auth/mfa/*` and `/auth/logout`.
- The refresh cookie is `lc_refresh`: `HttpOnly; Secure; SameSite=Lax; Path=/v1/auth`, host-only (no `Domain`), `Max-Age` up to 12 hours. `/auth/refresh` is the only route that reads it and requires an `Origin` in `AUTH_ALLOWED_ORIGINS` (`403 FORBIDDEN` first, OQ-90). Token responses carry `Cache-Control: no-store`.
- `logout` revokes the family; `logoutAll` every live session of the user (partial ones too). Both clear the cookie.

**MFA.** TOTP is on `node:crypto` (RFC 4226 and RFC 6238, tested against their vectors): 30 seconds, 6 digits, one step either side, every step of the window compared in constant time. The secret (160 bits) is encrypted by the `SecretCipher` port (AES-256-GCM with `AUTH_ENCRYPTION_KEY` for local and test; the KMS adapter comes with P3-11, and the blob format has a version byte so an envelope format can follow) and bound to its row by the AAD `mfa_factor:<id>`. **Replay:** `mfa_factor.last_used_step` (new column, see the migration `20261125100000_mfa_factor_replay_and_lockout`) records the last accepted step, and a step at or below it is refused; the update is conditional, so one code cannot be accepted twice even by simultaneous requests. **Lockout:** `failed_attempts` and `locked_until` (also new): 5 wrong codes in a row lock the factor for 15 minutes (`OTP_LOCKED`, `Retry-After`); the right code is refused while locked; a right code clears the count. The same limits apply to `confirmMfaEnrolment`. Enrolment: `startMfaEnrolment` makes a pending factor (a new start replaces an unconfirmed one; `409` once a factor is verified); `confirmMfaEnrolment` activates it and returns 10 recovery codes once (HMAC-stored, `XXXXX-XXXXX`), and does not issue a session, so the sign-in that follows needs a *new* code (the confirming step is already used). Recovery codes cannot sign anyone in (OQ-35).
- `verifyMfa` with a **partial** session revokes it (`MFA_COMPLETED`) and starts a new full session with `mfa_verified_at` set (new `sid`, refresh cookie). With a **full** session it is a step-up: `mfa_verified_at` of the live row is set to now and a new access token carries `mfa_at`; no cookie. A user with no verified factor gets `403 MFA_ENROLMENT_REQUIRED`.
- `assertStepUp(session, clock, maxAgeSeconds = 300)` (in `sessions.ts`) throws `STEP_UP_REQUIRED` (`meta.maxAgeSeconds`) unless `mfa_verified_at` is no older than that (and not in the future). Read the session from the database (`authenticateSession`), never from the token alone. The `MfaGuard` of P3-04 calls it (section 8).

**Database contexts (RLS).** `otp_challenge` is `platform_only` and `app_user` writes need `id = app_user_id()`, so the flows before a user is known run with `withDbContext(prisma, { kind: 'system' })` as the `app_rw` login role: OTP request and verification, sign-in and user creation, refresh, and the session lookup of the guard (the case `db-context.ts` names: "finding a session by its token"). Once the access token has identified the user, the work runs as `{ kind: 'tenant', orgId: '', userId }`: no organisation, so the policies `own_user` (`user_session`, `mfa_factor`, `mfa_recovery_code`), `membership_visibility` and `user_visibility` apply and a user sees only their own rows. The organisation of a request is never taken from the client: `X-Active-Membership` and `membershipId` only choose among the user's own active memberships (`404 NOT_FOUND` otherwise), and the composite foreign key (C-06) backs that in the database.

**Audit** (same transaction, no codes, tokens, secrets or addresses): `user.create`, `auth.signin`, `auth.session_revoke`, `auth.sessions_revoke_all`, `auth.refresh_reuse_detected`, `auth.mfa_enrol_started`, `auth.mfa_enrol_confirmed`, `auth.mfa_verified`, `auth.mfa_locked`, `auth.membership_switch`.

**Tests.** Unit: `packages/core/src/identity/*.test.ts`, `apps/api/src/modules/identity/*.spec.ts`. Database (real tables, grants, RLS, `app_rw`): `packages/core/test/db/identity-*.test.ts` (`pnpm test:db`). HTTP (`contractRequest`, real database): `apps/api/test/integration/` (project `http-db`, run by `pnpm test:contract`; see TESTING_STRATEGY section 8).

**Contract and document differences.**
- The OTP is emailed through the `EmailSender` the notifications worker uses (`EMAIL_TRANSPORT`): SES when deployed, Mailpit over SMTP on a developer machine (`SMTP_HOST`). The API refuses to start in production or UAT without a real sender. The message is sent directly after the commit, never through the outbox, the `notification` table or the templates; a failed send gives a bare 500 with no detail, and the code and the address are never logged or kept in the error (OQ-172).
- ADR-006 and this document put throttles in Redis; the OTP limits are counted in the database (OQ-88).
- The contract requires `Idempotency-Key` on every identity POST; it is accepted and ignored (OQ-87).
- The contract's `refresh` says only "cookie scoped to the API domain"; the path is limited to `/v1/auth` as well.
- `getMe` and `setActiveMembership` accept full sessions only (a partial token is `401`, as the contract lists no 403).
- Sign-in limits are constants (OQ-85); `report.publish_mfa_max_age_seconds` (300) is the only key that exists, and `assertStepUp` takes the age as a parameter.

## 8. As built (P3-04)

Code: the framework-free part is in `packages/core/src/identity/` (`actor.ts`, `resource-checks.ts`, `tenant-scope.ts`, `repository.ts`, `membership-repository.ts`); the Nest part is in `apps/api/src/modules/identity/` (`membership.guard.ts`, `permission.guard.ts`, `mfa.guard.ts`, `authorised.decorator.ts`, `current-actor.ts`). The guards belong to the identity module (MODULE_BOUNDARIES: identity exposes "guards, `CurrentActor`"); another module imports `IdentityModule` to use them.

**Protecting a route.** `@Authorised({ permission: 'booking.decide' })` stacks `AuthGuard` → `MembershipGuard` → `PermissionGuard` → `MfaGuard` in that order and maps core errors to problem responses. The options are a union, so one of three must be chosen: `permission` (one code, or a list that needs **all** of them), `anyPermission` (a list that needs **one**), or `noPermissionRequired: true` (any signed-in actor, also one with no membership; the handler checks what it needs). `stepUp: true | seconds` adds `MfaGuard`'s check. The pieces are also exported on their own: `@RequirePermission(...)`, `@RequireAnyPermission(...)`, `@NoPermissionRequired()`, `@RequireStepUp(maxAgeSeconds?)`, `@CurrentActor()`. A code that is not a permission throws when the route is declared, so a typo fails at start-up.

**`PermissionGuard` fails closed.** A route behind the guards with neither a permission declaration nor `@NoPermissionRequired()` is `403 FORBIDDEN`, and so is a request that reaches it with no actor. The check is role level: a permission the role holds as ○ or ◐ passes the guard and is enforced again by the domain service (`grantsFor`; OQ-105).

**`CurrentActor`** (`{ userId, sessionId, membershipId, orgId, orgType, roles, permissions, siteIds, allSites, mfaVerifiedAt, isPlatform }`) is built once per request by `MembershipGuard` from the session and the database (`loadCurrentActor`, run as the user alone). Nothing of the request is an input except `X-Active-Membership`, which only chooses among the user's own active memberships (`404 NOT_FOUND` for any other value, OQ-108).
- It is read on **every request**, so a deactivated membership, a revoked role or a `SUSPENDED`/`CLOSED` organisation is refused at once with `403 FORBIDDEN` while the access token is still valid (OQ-106, OQ-109). `permissions` is the union of `permissionsOf(role)` over the membership's roles that fit the organisation type.
- A user with no active membership has an actor with no organisation and no permissions: only `@NoPermissionRequired()` routes serve it.
- `siteIds` are the live `membership_site` rows (lab members); an empty list means no site (OQ-110). Platform staff have `allSites` and `isPlatform`.
- **MFA.** `AuthGuard` already refuses a partial session everywhere but `/auth/mfa/*` and `/auth/logout`, which is what stops an MFA-required user who has not finished sign-in. As a second line `buildCurrentActor` refuses a membership with an MFA-required role when the session never completed MFA (`401 STEP_UP_REQUIRED`, `meta.reason = MFA_REQUIRED_FOR_ROLE`, OQ-107): a role gained after sign-in cannot slip through. `MfaGuard` then handles `@RequireStepUp` with `assertStepUp` on the session row `AuthGuard` loaded on this request (`401 STEP_UP_REQUIRED`, `meta.maxAgeSeconds`).

**Resource checks** (`resource-checks.ts`, used inside the service's transaction): `assertSameOrg`, `assertPartyOrg` (customer or lab of a booking), `assertSiteInScope`, `assertNotSameUser` (Maker is not Checker, `403 SELF_APPROVAL_FORBIDDEN`), `assertPermitted`, `assertVisible`, `assertAccess`. They throw `IdentityError`, which `@Authorised` maps to the problem response. The 404-versus-403 rule: the role-level 403 comes from the guard and does not depend on the resource; a resource that is unknown or out of the actor's scope is then 404; only an in-scope resource can be 403. Platform staff pass the organisation and site checks; their access is role-based (OQ-111).

**Platform staff and `x-roles`.** A platform actor has `isPlatform` and `allSites`, and runs in the `platform` database context. Admin routes use the same `@Authorised({ permission })` as any other; the contract's `x-roles` is not enforced separately, because that would be a second source of truth for who may do what. `apps/api/test/admin-roles-permissions.spec.ts` compares the two and prints the operations where no permission is held by exactly the roles `x-roles` names (10 of 73 today, OQ-112); it does not fail. Acting on behalf of an organisation is `TenantScope.runOnBehalfOf` (see TENANT_ISOLATION section 5).

**Not changed by P3-04:** `getMe` and `setActiveMembership` keep `AuthGuard` only (a user with no membership must be able to call them).
